# Signing

Servika publishes two things a server has to be able to trust: the malware rule
package and the release checksum list. One Ed25519 key signs both.

The key's whole value is that it is **not** on the machine that publishes the
artefacts. `SHA256SUMS` and the bundles it describes go to the same GitHub
release under the same token, so a key held in a repository secret would be
reachable by anybody who can rewrite the artefacts, and its signature would
prove nothing the checksum does not already prove. Signing happens on the
maintainer's own machine, and that is what turns GitHub into untrusted
infrastructure for this purpose.

Until the key exists, every path below is skipped in silence. An installation
that is running today keeps behaving exactly as it does today.

## Current state

Three placeholders are empty and hold the feature off:

| File | Line | Placeholder |
|------|------|-------------|
| `internal/antivirus/remoterules.go` | 80 | `var rulePublicKeyHex = ""` |
| `install.sh` | 66 | `SERVIKA_RELEASE_PUBKEY=''` |
| `assets/ops/servika-update` | 182 | `SERVIKA_RELEASE_PUBKEY=''` |

With them empty: the panel never fetches a rule package, the scan worker and
the watcher never read one, and neither installer checks a release signature.
The built-in rule set and the existing SHA256SUMS check carry on unchanged.

## 1. Create the key (once, on your own machine)

```bash
go run scripts/servika_sign.go -genkey ~/.servika-signing-key
```

It writes the private half at mode 0600 and refuses to overwrite an existing
file, because replacing a key stops every server carrying the old public half
from adopting anything.

It prints the public half in the two forms the tree needs: a hex string for Go
and a PEM block for the shell scripts. **The public half is not a secret** and
belongs in the repository. The private half never goes into git, into CI, or
onto any server.

Back the private key up somewhere you control. Losing it means generating a new
one and shipping a panel release that carries the new public half; every server
still on the old build stops adopting rule packages until it updates.

## 2. Embed the public half

Paste the printed values into the three placeholders above:

- `internal/antivirus/remoterules.go` takes the **hex** form.
- `install.sh` and `assets/ops/servika-update` take the **PEM** block, inside
  the single quotes, keeping the `BEGIN`/`END` lines.

A build can also inject the Go side instead of editing the file:

```
-ldflags "-X servika/internal/antivirus.rulePublicKeyHex=<hex>"
```

From this point on the release signature is **required**, including when the
`.sig` file is absent. "Verify it if the signature is present" is not a check,
because an attacker who can replace the artefacts can simply not publish one.
Older tags that were released without a signature can no longer be installed by
these scripts. That is deliberate.

## 3. Sign each release (after CI publishes it)

CI cannot do this step. The key is not there, and `SHA256SUMS` is generated by
the release job, so it does not exist to be signed until the job has run. The
release workflow prints these commands when it finishes:

```bash
gh release download vX.Y.Z -p SHA256SUMS -D /tmp/svk
go run scripts/servika_sign.go -key ~/.servika-signing-key \
     -detached /tmp/svk/SHA256SUMS
gh release upload vX.Y.Z /tmp/svk/SHA256SUMS.sig
```

Between the release being published and the signature being uploaded, an
installer carrying the public key refuses that tag. That is the correct
direction to fail, but it means the gap should be short.

Check it from a clean machine before announcing the release:

```bash
curl -fsSL https://raw.githubusercontent.com/ServikaPanel/servika/main/install.sh \
  | SERVIKA_RELEASE_TAG=vX.Y.Z sudo bash
```

You should see `✓ release signature verified` before `✓ checksum verified`.

## 4. Publish a rule package (optional, and only when you want one)

The panel's own detection rules ship inside the binary and need none of this.
A package is only worth publishing when you want to add a pattern between
releases.

Write the rules as JSON:

```json
{
  "rules": [
    {
      "name": "PHP.Webshell.SomeNewShape",
      "score": 60,
      "pattern": "(?i)some\\s*\\(\\s*pattern",
      "kind": "php"
    }
  ]
}
```

- `name` must be dotted and must not take a built-in rule's name.
- `score` is capped at 60 whatever you write, and a critical verdict always
  needs a built-in match beside it. A packaged rule can raise a file to
  `suspicious`; it can never on its own cause the panel to move a customer's
  file.
- `kind` is `php`, `js`, `htaccess` or `any`. A package cannot name a file type
  the scanner does not open.
- The pattern is Go RE2, so no backreferences and no lookaround.

Sign it with a version **higher than the last published one**:

```bash
go run scripts/servika_sign.go -key ~/.servika-signing-key \
     -rules rules.json -version 2 -out assets/av/rules.svkav
```

The tool checks the rules against the scanner's own acceptance logic first and
tells you how many it will actually use. It refuses a set nothing survives,
because such a package verifies perfectly and detects nothing.

Commit `assets/av/rules.svkav` and push to `main`. Panels fetch it from
`https://raw.githubusercontent.com/ServikaPanel/servika/main/assets/av/rules.svkav`
every six hours, verify the signature, and adopt it if the version is higher
than what they have.

**Re-sign at least every 60 days.** A signature proves who made a package, not
when. Past `RemoteRuleMaxAge` a package is refused and the panel falls back to
the built-in set, which is what it runs with no package at all. This is on
purpose: without an age limit, anyone who can merely withhold the new package
pins a server to old rules forever with every check still passing.

## Checking which rule set a server is on

A package past its age limit is refused and the built-in set takes over. That is
the correct behaviour, but it is also the one event you have to act on, so three
places report which set is in force:

```bash
servika-server -print-av-rules
```

```
configured=yes        this build carries a signing key
source=package        builtin when no package is in force
cache=verified        verified | absent | stale | refused
version=2
produced=2026-08-21T09:14:02Z
rules=1
age_days=0
max_age_days=60
```

`age_days` comes from the SIGNED `produced` stamp, never from the cache file's
mtime. The panel writes that file only when a NEWER version arrives, so its
mtime says when a new version last landed, and a server whose rule set has not
changed in a month would look stale on that reading while being perfectly
healthy.

`servika-verify` reports the same thing. No signing key is a PASS, because that
is the default on every installation. A package within its age limit is a PASS
with its version and age. Everything else is a WARNING, including a package past
80 percent of the limit, which is your notice to publish a new one before the
fallback happens rather than after.

The antivirus settings screen carries one line for it beside the detection
layers, and the API answers it as `rule_set` on `GET /admin/antivirus/settings`.

## What a package cannot carry

A packaged rule is one regular expression over one file's bytes, plus a weight
and a file kind. Ten of the panel's detections cannot be expressed that way and
stay compiled into the binary:

| Detection | Why it cannot travel |
|---|---|
| `PHP.Taint.RequestNameExecuted` | Collects assigned variable names in one pass, then matches a second pattern and compares the captured name against that set. RE2 has no backreferences, so one expression cannot do it. |
| `PHP.Taint.RequestValueToSink` | Same two-pass name comparison. |
| `PHP.Obf.ConcealedFunctionName` | Rewrites the file (strips `'ev' . 'al'` seams), searches the rewritten text, and requires the name to be **absent** from the original. Two different texts; a pattern sees one. |
| `PHP.Obf.HighEntropyLine` | Computes Shannon entropy per line and compares it to 5.9. Arithmetic, not matching. |
| `Location.UploadsExecutable` | Judges the path relative to the scan root, not the file's contents. |
| `Location.CacheExecutable` | Same. |
| `Location.WellKnownExecutable` | Same. |
| `Location.DoubleExtension` | Same. |
| `Location.HiddenDirectory` | Splits the path into segments and consults an allow-list of ordinary dotted directories. |
| `WP.Core.ExtraFile` | Comes from comparing the tree against wordpress.org's published checksum table. There is nothing to pattern-match. |

This is a property of the format, not an oversight, and widening it would be a
mistake. A package that could carry **code** would turn a signing-key
compromise into remote code execution on every server that adopts it. A package
that can only carry a capped regular expression cannot, however the key is
handled.

## Verifying by hand

The rule package:

```bash
head -c 8 assets/av/rules.svkav    # SVKAV001
```

The release signature, with the public PEM in `pub.pem`:

```bash
openssl pkeyutl -verify -pubin -inkey pub.pem -rawin \
  -in SHA256SUMS -sigfile SHA256SUMS.sig
```

`openssl` 3.x ships with AlmaLinux 9 and 10; the ops scripts install it if it
is missing.

## Turning it back off

Empty the three placeholders. Every path returns to being skipped in silence:
panels stop fetching, installers stop checking a signature, and the built-in
rule set carries on. Nothing has to be uninstalled and no server is left in a
half-configured state.
